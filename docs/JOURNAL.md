# Журнал (чёрный ящик) — система памяти, зависимостей и отката

Полная память о действиях агентов: что было сделано, зачем, кем, в какой
последовательности, с зависимостями — с возможностью воссоздать (replay)
и вернуть всё как было (rollback).

---

## 1. Зачем это нужно

Без журнала система-агент «вслепую»: правки накапливаются, и когда что-то
ломается, невозможно ответить на вопросы:

* **кто и зачем** изменил этот файл? (агент `file` в задаче «добавь роут», вторник 14:32)
* **что именно** изменилось — и можно ли увидеть diff?
* **в каком порядке** выполнялись действия и что от чего зависело?
* как **откатить** изменения одной задачи, не откатывая остальные?
* как **воспроизвести** те же действия на чистой копии проекта?

Журнал отвечает на все пять вопросов автоматически, без участия человека.

---

## 2. Принципы дизайна

| Принцип | Реализация |
|---|---|
| **Append-only** | События только добавляются, никогда не редактируются. Откаты и replay — тоже события. |
| **Тройная запись** | SQLite-индекс (поиск, связи) + JSONL-поток (полные данные, crash-safe) + тени файлов (содержимое). Каждый носитель самодостаточен. |
| **Один перехват — всё захвачено** | Все tool calls идут через `MCPManager.call_tool` — журналирование встроено туда одним хуком. Ни один агент не может «забыть» записаться. |
| **Ноль новых зависимостей** | Только stdlib + уже установленные fastapi/mcp. Python 3.14 и Windows 10 совместимы. |
| **Отказоустойчивость** | SQLite в WAL-режиме; JSONL с блокировками; отказ журнала не ломает основную работу (все хуки в try/except). |
| **Память до последнего байта** | Ретенция удаляет содержимое только в крайнем случае: сначала сжатие (5–15×), потом старые архивы. Метаданные (индекс, JSONL-ссылки, отчёты) не удаляются никогда. |
| **Честность об обратимости** | Каждое событие помечено: `reversible=1` (есть тени — откат гарантирован), `2` (частично, напр. SQL), `0` (необратимо). Система никогда не обещает того, чего не может. |
| **Секреты не утекают** | Аргументы с ключами `password/token/api_key/...` маскируются до записи. |

## 3. Что записывается

| Вид события | Когда | Пример |
|---|---|---|
| `session` | WS-подключение пользователя | `session_start`, `session_end` |
| `task` | Каждый запрос пользователя через оркестратор | `task_start` (запрос, маршрут, модель), `task_end` (статус, счётчики) |
| `tool_call` | **Каждый вызов MCP-инструмента** | `filesystem.write_file → src/app.py`, с аргументами, результатом, хэшами до/после, тенями |
| `file_change` | Внешние изменения файлов (watcher, опция) | правки руками в редакторе |
| `rollback` | Каждый откат | какие события отменены, конфликты |
| `replay` | Каждое воспроизведение | сколько шагов выполнено |
| `system` | Старт/стоп, ретенция, смена проекта | `startup`, `retention_sweep` |

### Связи (граф зависимостей)

Каждое событие связано с другими тремя способами:

1. **`parent_id`** — предыдущее событие той же задачи (цепочка выполнения);
2. **`depends_on`** — явные зависимости (агент может указать);
3. **`target:`-рёбра** — события, касавшиеся одного файла, связываются
   автоматически: «эта правка отталкивалась от той».

Вместе это DAG → топологический порядок → точные replay-планы и откаты
в правильном порядке (последние правки отменяются первыми).

### Контекст: кто, зачем, в рамках чего

```
session_id ─┬─ task_id (запрос, маршрут оркестратора)
            │    └─ agent_id (file / mysql / postgres / …)
            │         └─ loop_id + iteration (шаг цикла)
            └─ trace_id — сквозной идентификатор для диагностики
```

Контекст передаётся через `contextvars` — наследуется всеми вложенными
asyncio-задачами автоматически. Агентам не нужно ничего передавать вручную.

## 4. Тени файлов — основа отката

Перед каждой правкой файла:

```
data/journal/shadows/2026-09-19/{event_id}/
├── before/src/app.py          ← копия ДО
├── after/src/app.py           ← копия ПОСЛЕ (для diff и аудита)
├── manifest.before.json       ← existed, sha256, размер
└── manifest.after.json        ← то же + связь с before
```

* Большие файлы (> `JOURNAL_SHADOW_MAX_MB`, по умолчанию 50 МБ) не
  копируются — фиксируется только хэш (событие остаётся честным:
  `reversible=0`).
* Бинарники не диффируются, но тенятся и откатываются.
* **Конфликт-детекция**: при откате текущий хэш файла сверяется с
  `after`-манифестом. Если файл менялся после события — в safe-режиме
  файл пропускается с пометкой `conflict` (откат не затрёт чужую правку).
  `force=true` переопределяет.

## 5. Откат (rollback)

| Скоуп | Как вызвать |
|---|---|
| Одно событие | `journal_rollback {event_id}` |
| Вся задача | `journal_rollback {task_id}` |
| Вся сессия | `journal_rollback {session_id}` |
| Всё после точки | `POST /api/journal/rollback {event_id}` (rollback_to_point) |

Порядок работы движка:

1. Собирает изменяющие события → топологический порядок → инвертирует.
2. **Dry_run по умолчанию** — показывает план, ничего не трогает.
3. Перед откатом каждого события создаёт «предохранительный трос» —
   тень текущего состояния (сам откат откатываем!).
4. Восстанавливает `before`-тени; для созданных файлов — удаление.
5. Конфликт-детекция по хэшам (см. выше).
6. Пишет `rollback`-событие с полным списком отменённого (аудит откатов).

Ограничения (честно):
* SQL-события (mysql/postgres) — `reversible=2`: откат пропускает их с
  пометкой (полный откат БД требует before-снапшотов таблиц — поле для
  развития);
* события со `reversible=0` (shell/git, чтение) не откатываются;
* тени, сжатые ретенцией в архив, перед откатом нужно распаковать
  (движок подскажет имя архива).

---

## 6. Воспроизведение (replay)

Два сценария использования:

1. **Развернуть те же действия на чистой копии проекта** — план
   (`journal_replay_plan`) — упорядоченный список tool calls с аргументами
   и контекстом. Выполнение: `POST /api/journal/replay/execute` (через
   реальный MCPManager, с approval gate) или агент сам выполняет шаги
   своими инструментами, читая план.
2. **Расследование** — план читаем как «сценарий того, что делали агенты»:
   шаг за шагом, с аргументами и агентами.

Экспорт: `GET /api/journal/replay/export` — план сохраняется в файл
(`reports/replay-*.json`).

---

## 7. Ретенция: «память копится, пока есть место»

Логика (проверяется при старте и каждые `JOURNAL_SWEEP_INTERVAL` секунд):

```
Свободно на диске > JOURNAL_MIN_FREE_GB (5 ГБ)?
├── ДА  → НИЧЕГО не делаем. Копим всё.
└── НЕТ → Эскалация:
    1. Сжать тени дней старше JOURNAL_COMPRESS_AFTER_DAYS (3) в zip
       (текст сжимается в 5–15 раз) + несжатые оригиналы удалить.
    2. Всё ещё мало? Сжать старые JSONL в zip.
    3. Всё ещё мало? Удалить СТАРЕЙШИЕ zip-архивы (от старых к новым).
```

**Никогда не удаляются**: `journal.sqlite` (индекс всех событий),
`reports/*.md`. После этапов 1–2 содержимое правок доступно в архивах.
После этапа 3 остаются метаданные: что и когда делалось, с какими
аргументами и хэшами — но не содержимое файлов тех лет.

Дополнительно: `JOURNAL_MAX_SHARE_PERCENT` — ограничение доли диска
(0 = выключено).

Каждый проход ретенции сам записывается в журнал (`retention_sweep`) —
видно, когда и почему что-то сжималось.

## 8. Интерфейсы доступа

### 8.1. Для агентов (MCP) — `mcp_servers/journal/`

| Инструмент | Назначение |
|---|---|
| `journal_query` | выборка событий (kind, task, agent, target, mutating…) |
| `journal_search` | полнотекстовый поиск (FTS5) |
| `journal_get` | полное событие: аргументы, результат, тени |
| `journal_timeline` | хронология текстом (готово для LLM) |
| `journal_stats` | статистика, размер, диск, статус ретенции |
| `journal_provenance` | полная история изменений файла/таблицы |
| `journal_rollback` | откат (dangerous, dry_run по умолчанию) |
| `journal_replay_plan` | план воспроизведения |

### 8.2. HTTP API — `/api/journal/*` (18 эндпоинтов)

```
GET  /api/journal/events            фильтры: kind, task_id, agent_id, target, mutating…
GET  /api/journal/event/{id}        полное событие (+файлы теней)
GET  /api/journal/event/{id}/diff   unified diff до/после
GET  /api/journal/search?q=         поиск
GET  /api/journal/timeline          текстовая хронология (для LLM)
GET  /api/journal/graph             узлы+рёбра DAG (format=mermaid — текст)
GET  /api/journal/provenance?target=
POST /api/journal/rollback          {event_id|task_id|session_id, mode, force}
POST /api/journal/rollback/verify   сверка текущих хэшей с журналом (drift)
POST /api/journal/replay/plan       построить план
POST /api/journal/replay/execute    выполнить план (mode=dry_run|execute)
GET  /api/journal/replay/export     экспорт плана в файл
GET  /api/journal/stats             статистика
GET  /api/journal/retention         статус ретенции
POST /api/journal/retention/sweep   запустить проход вручную
GET  /api/journal/export            экспорт событий (json|md)
GET  /api/journal/reports           список отчётов
```

### 8.3. Для людей и LLM — файлы

* `reports/session-*.md`, `reports/task-*.md` — готовые отчёты: таймлайн
  таблицей, изменённые цели, возможности отката. **LLM может просто
  прочитать файл** (filesystem.read_file) — это самый простой интерфейс
  для моделей.
* `events/events-YYYYMMDD.jsonl` — полный поток (по строке на событие).
* `journal.sqlite` — для сложных запросов напрямую (WAL — читается из
  любого процесса, даже во время работы системы).

### 8.4. CLI

```cmd
python -m src.journal.cli status                    :: сводка
python -m src.journal.cli events --mutating         :: последние правки
python -m src.journal.cli show {event_id}           :: событие целиком
python -m src.journal.cli search "app.py"           :: поиск
python -m src.journal.cli timeline {task_id}        :: хронология задачи
python -m src.journal.cli provenance src\app.py     :: история файла
python -m src.journal.cli graph {task_id}           :: mermaid-граф
python -m src.journal.cli rollback {event_id}       :: план отката (dry)
python -m src.journal.cli rollback task:{task_id} --execute
python -m src.journal.cli replay {task_id}          :: план воспроизведения
python -m src.journal.cli sweep                     :: ретенция сейчас
python -m src.journal.cli report {task_id}          :: markdown-отчёт
```

### 8.5. Веб-интерфейс

⚙️ Настройки → вкладка **📓 Журнал**: статистика (события, размер, диск),
фильтры (вид/задача/поиск/только правки), таблица событий, детальный
просмотр с **Diff**, **планом отката** и **откатом** (dry/execute),
план воспроизведения задачи.

## 9. Типовые сценарии

**«Что сломалось?»** — журнал показывает последнюю правку файла до ошибки:
`python -m src.journal.cli provenance src\app.py` → последнее событие с
diff → откат одной правки.

**«Отмени всю задачу»** — `journal_rollback {task_id}` (сначала dry_run).

**«Что делал агент вчера?»** — `journal_timeline` по сессии или отчёт
`reports/session-*.md`.

**«Почему файл такой?»** — провенанс даёт цепочку правок с хэшами и
авторами (какой агент, какая задача).

**«Диск заполняется»** — ничего: ретенция сама сожмёт старое; при желании
`POST /api/journal/retention/sweep` и посмотреть отчёт.

---

## 10. Гарантии и границы

**Гарантируется:**
* каждое действие агента через MCP записано (перехват в единой точке);
* каждая правка файла имеет тени ДО и ПОСЛЕ (в пределах лимита размера);
* откат в правильном порядке с конфликт-детекцией и аудитом;
* метаданные истории не теряются никогда (пока жив диск под индекс);
* отказ журнала не останавливает основную работу системы.

**Не покрывается (честно):**
* содержимое СУБД до/после SQL-запросов (только текст запроса) — для
  полного отката БД подключите снапшоты таблиц отдельной задачей;
* действия shell/git вне MCP (внешние команды) — watcher фиксирует
  изменения файлов, но не их автора;
* файлы больше лимита теней (фиксируется хэш, без содержимого);
* содержимое, удалённое ретенцией на этапе 3 (крайний случай).

## 11. Развитие (дальнейшие шаги)

1. **DB-снапшоты**: перед mutating-SQL — дамп затрагиваемых таблиц
   (малые таблицы) → полный откат БД.
2. **Git-зеркало**: авто-коммит теней в служебный git-репозиторий —
   удобный diff/history поверх теней.
3. **Semantic-слой**: индексация отчётов в векторную память проекта —
   «найди похожие прошлые правки».
4. **COM/TCP-мониторинг**: те же события для аппаратных каналов
   (упоминалось в концепции мониторинга).
5. **Мульти-инстанс**: экспорт событий в Redis broker для нескольких
   процессов.
